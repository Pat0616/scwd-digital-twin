# SCWD Sorsogon Water Monitor: web app (scwd-mock2)

The Sorsogon City Water District's **Sorsogon Water Monitor** (the QGIS project `SorsogonWater_Monitor.qgz`) as a
Next.js app, with live status from the Azure Digital Twins (ADT) instance. It is wired the same way as
`C:\Users\pagda\water-gis\scwd-frontend`: static GIS from a QGIS web export, the twin read on the server only, and
the status pushed to the browser over Server-Sent Events. The page is a port of the Monitor project's own web page
(the plugin's `monitor_template.html`): the same status-first design, views, barangay focus and search.

```
npm install
npm run dev          # http://localhost:3000, live from ADT_URL (set it in .env.local and run `az login` first)
```

Other scripts: `npm test` runs the status tests (Vitest). `npm run lint`, `npm run typecheck` and `npm run build`
do what their names say.

## How it fits together

| Piece | Where | What |
|---|---|---|
| Static GIS | `public/gis/*.json`, `relief*.png` | The Monitor project's stations, pipes, gauges, valves, zones and barangays, plus its look (state colours, badges, icons, palette, relief). Generated by `npm run import-gis`. Don't edit by hand. |
| Twin source | `src/lib/twin/` | `TwinSource` returns `{ twins, relationships }`: the live ADT instance (default), or the v4 graph file. Shared reads, at most one every 2.5 s. |
| Twin rules | `src/lib/status/` | scwd-frontend's rules (`twin_sync.py`, `map_look.py`): readings, alarm text, pressure bands, barangay supply status. |
| Monitor rules | `src/lib/monitor/status.ts` | The plugin's `monitor_status.py`: one plain state and headline per station, equipment group, gauge and barangay; the speech bubble's problem parts; "what to do" and "affects"; the city's one-line summary. |
| API | `GET /api/status` | Both statuses, keyed by twin id (barangays by their GIS id). |
| | `GET /api/status/stream` | The same, pushed whenever the twin changes (SSE). |
| | `GET /api/twin/[id]` | One twin with its parts and readings. |
| Page | `src/components/` | MapLibre. Loads `/gis/*` once and listens to the stream; merges each update by `twin_id`, no reload. |

### The join: GIS `twin_id` = twin `$dtId`

| GIS feature | `twin_id` | Twin model |
|---|---|---|
| Station | `pumpstation-NN` | `PumpingStation` (its parts are `partOf` it) |
| Bulk supply point | `bulk-casiguran-wd` | `BulkSupplyPoint` (water bought in; its readings are on itself) |
| Gauge: pressure point (DPP) | `dpp-<barangay>-<n>` | `DPP` |
| Gauge: far-point chlorine | `farpoint-<barangay>` | `FarPointSite` |
| Pipe segment | `pumpstation-NN-transmission` or `<barangay>-distribution` | `TransmissionPipe` / `DistributionPipe`. Many segments share one twin pipe. |

Twin v4 has no Sensor twins: each reading is a property of the part it measures (e.g. `pressure_psi`,
`pressure_psi_min`, `pressure_psi_alarm`, `pressure_sensor_online`, `readings_at`); `src/lib/twin/readings.ts` reads them.
A feature with `twin_id: null` is on the official map but not in the twin yet ("Not in the digital twin yet").
Until the twin has answered, twin-backed stations, gauges and barangays show "Waiting for the digital twin…", never
the values in the GIS export.

## Updating the GIS (re-export from QGIS)

1. Open `SorsogonWater_Monitor.qgz` in QGIS and export its web page with the water-network plugin (Monitor panel).
   It writes `index.html`, `data.js` and the relief images to `C:\Users\pagda\water-gis\web-monitor\`.
2. Run:
   ```
   npm run import-gis                        # reads ~/water-gis/web-monitor/data.js
   npm run import-gis -- D:\path\to\data.js  # or another Monitor export
   ```
   This writes `public/gis/*.json`, copies the relief images and prints how many features are linked to the twin.
   Reload the page to see the new geometry. The script refuses an export that is not the Monitor project's.

**Background (the QGIS project's own map, no online basemap).** The map draws the Monitor project's background
layers exactly as the plugin styles them (`monitor_style.py`): Outside Mask (sea), Sorsogon Municipalities (land,
borders, names, and the "SCWD water: …" summary under Sorsogon City in the province view), Province relief,
Municipality borders, Sorsogon Barangays (land, borders, the city's barangay names), City relief, Served Area and
Streets. They are not in the web export; write them from the project's GeoPackages with:

```
npm run import-background                        # reads ~/water-gis/data, uses QGIS's ogr2ogr
npm run import-background -- D:\path\to\data
```

The map is held to the province (it cannot pan or zoom out past it). Only the label fonts come from the internet
(OpenFreeMap's font server).

## Twin source

Settings go in `.env.local` (git-ignored, server only); `.env.example` lists them all.

* **`TWIN_SOURCE=adt`** (default): the live instance at `ADT_URL`. The server queries `SELECT * FROM digitaltwins` and
  `SELECT * FROM relationships` with `@azure/digital-twins-core` and `DefaultAzureCredential`: a service principal
  (`AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, with the **Azure Digital Twins Data Reader** role), or
  your own `az login` when those are empty.
* **`TWIN_SOURCE=file`**: the v4 graph, `data/scwd_digital_twin_adt_v4.json` (an ADT Explorer export; or
  `TWIN_JSON_PATH`). It is re-read whenever the file changes, so editing a copy while the app runs updates the page.
* **`TWIN_AS_OF_NOW=true`** moves the readings' times so the newest is now, as the plugin's `JsonSource` does. The
  instance currently holds a snapshot whose readings are from 4 Nov 2026; without this every reading is older than
  a day and shows as "No current reading". On by default for the file, off for ADT; `.env.local` turns it on. The
  page badge says "reading times moved to now (demo)" while it is on.

**Live updates.** While at least one browser has the page open, the server reads the twin every 3 s and compares
every twin's and relationship's `$etag`. When anything changed it pushes the new status to every open page; markers,
cards, the attention list and an open detail panel update in place. The badge says "Live from Azure Digital Twins ·
checked hh:mm:ss · latest reading …". If the twin can't be read the page keeps the last status and says "Twin
unreachable"; `GET /api/status` answers 502 (details in the server log only).

## Status rules (mirror the QGIS plugin)

* **States**, worst first: Not working (red square), Needs attention (amber triangle), No current data (grey dashed
  ring), Working (green circle), Not in the digital twin yet.
* **Equipment groups**: water source, treatment, pump, pump drive (VFD), storage tank, grid power, generator.
* **A station** is Not working when it is down or its pumping is down; a part down while it still pumps is Needs
  attention. Its headline is its worst problem in plain words ("Pump stopped (+4 more)"); a standby station's
  stopped pump is not a problem.
* **Pressure points**: very low < 3 psi (Not working), low 3–7, OK 7–80, high > 80; an offline gauge is "Not
  reporting"; a reading older than 24 h is "No current reading". **Chlorine** OK at 0.3–1.5 ppm.
* **Data health**: a sensor silent for more than 1 h is late.
* **Barangays** take their supply status (scwd-frontend's `_bgy_status`) and the worst problem of the stations and
  gauges in them.

`tests/monitor.test.ts` runs the v4 graph through these rules and checks that every station (state, headline,
issues, card groups and readings, action, affects), gauge, barangay and the city line match what the QGIS Monitor
project exported.

## Notes

* The basemap comes from OpenFreeMap (Positron), so the page needs internet access for the basemap tiles.
* The station "since" time starts from the QGIS export and then follows the changes this server sees.
